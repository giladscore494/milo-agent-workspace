# Deployment preparation

Status: command plans and validation `COMPLETED_IN_CODE`; every actual
deployment step is `REQUIRES_MANUAL_OPERATOR_CONFIGURATION`. No CI job and
no script in this repository deploys anything.

## Immutable images

- Tags are the **full 40-character Git commit SHA**. Mutable identifiers
  (`latest`, `prod`, `stable`, branch names) and short SHAs are rejected by
  `generate-deployment-plan.sh` and the manifest validator;
  `scripts/deploy/cloud-run.sh` derives its tag from `git rev-parse HEAD`
  and refuses to run unless it matches `^[0-9a-f]{40}$`.
- `--revision-suffix rel-<SHA12>` is a Cloud Run *revision name*, not an
  image reference — revision names are length limited. Image identity is
  always the full SHA and is verified against the registry digest after
  deployment.
- API and worker are built separately from `Dockerfile.api` and
  `Dockerfile.worker`:

      <GCP_REGION>-docker.pkg.dev/<GCP_PROJECT_ID>/<ARTIFACT_REGISTRY_REPOSITORY>/api:<FULL_SHA>
      <GCP_REGION>-docker.pkg.dev/<GCP_PROJECT_ID>/<ARTIFACT_REGISTRY_REPOSITORY>/worker:<FULL_SHA>

- These two repository paths are the single canonical image identity. They
  are defined once in `scripts/deploy/deployment-contract.sh` and sourced by
  `cloud-run.sh`, `generate-deployment-plan.sh` and
  `generate-rollback-plan.sh`, so the plan can never instruct an operator to
  deploy an image the executable script does not build (and for which no
  rollback target exists). `tests/test_deployment_tool_alignment.py` runs
  both tools and compares what they emit.

- Build metadata is attached as non-secret OCI labels
  (`org.opencontainers.image.revision` = commit SHA, `…image.title` =
  component, plus build timestamp via `…image.created`); images embed no
  secret values, credentials, Supabase keys, provider keys or Redis URLs
  (CI verifies image history contains no secret-looking material).

## Strict deployment order

Generated by `scripts/release/generate-deployment-plan.sh --release-sha
<FULL_SHA>`; summary:

1. verify migration readiness (`check-migration-state.sh`);
2. verify execution flags are off (`smoke-test-execution-disabled.sh`);
3. confirm **no provider key is already bound** to the live API service or
   worker job (read-only; stop here if one is — see "Legacy provider
   bindings" below);
4. build both images;
5. push both images manually;
6. record the current worker/API bindings — variable names **and** secret
   references, with secret name and version (the "before" snapshot that
   proves nothing is dropped or repointed);
7. deploy/update the **private worker job first** (never execute it);
8. verify worker job configuration without executing it;
9. deploy/update the **private Cloud Run API**;
10. verify the API revision: image digest = pushed digest, runtime identity,
    required variable **names** (including the gateway identity pair), secret
    **references**, absence of any provider key, and the before/after
    preservation diff;
11. verify private ingress and invoker policy (no `allUsers` anywhere);
12. configure the Vercel server environment;
13. deploy Vercel;
14. Stage A read-only validation;
15. later stages only with explicit operator approval
    ([STAGED_ACTIVATION.md](STAGED_ACTIVATION.md)).

The worker job is never executed as part of deployment or verification:
the plan contains no `gcloud run jobs execute`, and `cloud-run.sh` compares
the job's execution list before and after the deployment and fails if it
changed.

## Non-destructive configuration updates

Every deployment command uses `--update-env-vars` and `--update-secrets`.
The `--set-env-vars` / `--set-secrets` forms are **forbidden**: they replace
the entire environment (or secret) block, silently deleting every
production variable and secret binding not repeated in that one command —
gateway audience, approved identities, budget caps, rate limits and worker
audience among them. `--clear-env-vars` / `--clear-secrets` are likewise
forbidden.

The guarantee is enforced in three places:

- `scripts/deploy/cloud-run.sh` uses only the `--update-*` forms, snapshots
  the live bindings **before** deploying, and fails the deployment if any
  pre-existing binding is missing afterwards;
- `scripts/release/generate-deployment-plan.sh` refuses to emit a plan whose
  commands contain a `--set-*`/`--clear-*` flag (`env-update-mode` check),
  and the plan itself carries a `comm -23 <before> <after>` preservation
  proof for both the API service and the worker job;
- `tests/test_cloud_run_deploy_static.py`,
  `tests/test_cloud_run_deploy_apply_mock.py`,
  `tests/test_deployment_plan_hardening.py` and
  `tests/test_deployment_tool_alignment.py` fail if either script regresses.

### Preservation compares full binding identity

The comparison is not name-only. Each binding is recorded as its variable
name plus, for a secret-backed variable, the secret name and version it
reads (`secret SUPABASE_SERVICE_ROLE_KEY SUPABASE_SECRET_KEY:latest`). A
binding **repointed** at a different secret — or at a different version of
the same secret — keeps its name while changing what the runtime actually
reads, so a name-only check would call it preserved. Both the executable
script and the generated plan fail on a remap exactly as they fail on a
removal; `cloud-run.sh` reports which secret moved and where to.

Comma-containing values (`ALLOWED_CORS_ORIGINS`,
`MILO_APPROVED_GATEWAY_IDENTITIES`) are passed with gcloud's alternate
delimiter syntax (`^;^K=V;K=V`), so a multi-origin list stays one value.
The delimiter is `;` and not `@`: every entry in
`MILO_APPROVED_GATEWAY_IDENTITIES` is a service account email, so an `@`
delimiter would split the allowlist mid-address.

### Non-destructive cuts both ways

Preserving what the command does not mention is the point — but it means a
binding this release considers forbidden is preserved just as faithfully as
one it considers required. `--update-secrets` removes nothing. So a
configuration that is wrong *before* the deployment is still wrong after it,
and the deployment will happily carry it forward. That is why the Stage A
provider-key rule is enforced against the **live** configuration before any
mutation, not only against what this release sets — see below.

## Stage A posture pinned by the deployment

Both the API service and the worker job are deployed with `JOB_LAUNCHER`
set to the selected launcher mode (default `disabled`) and with every
execution flag pinned off — `MILO_ENABLE_RUN_CREATION`,
`MILO_ENABLE_PROPOSAL_MUTATIONS`, `MILO_ENABLE_PROPOSAL_READS`,
`MILO_ENABLE_RUN_CANCELLATION`, `MILO_ENABLE_EXECUTION_CONTROL`,
`MILO_ENABLE_PAID_EXECUTION` all `false` (the canonical list in
`backend/production_config.py`). Enabling a stage is a deliberate,
separate operator action; a release never flips a flag on.

### No provider key exists at Stage A

`KIMI_API_KEY` / `MOONSHOT_API_KEY` are bound to **nothing** during Stage A
— not to the API service, and not to the worker job. Stage A performs no
provider call, so a reachable provider credential is blast radius with no
purpose: it can only be spent by a mistake. Concretely:

- neither key appears in `REQUIRED_SECRETS`, so Stage A does not even
  require the secret to exist;
- `require_no_provider_key_bindings` fails preflight — before anything is
  built — if a future edit reintroduces the binding on either resource;
- post-deployment verification fails if either name appears on either
  resource, whether as a secret reference **or** as a plain environment
  value (a key pasted in literally is just as reachable);
- the generated plan's `provider-key-scope` check refuses to emit a plan
  whose worker or API deploy command mentions a provider key.

The key is introduced by a separate, explicit **Stage C** operator action
([STAGED_ACTIVATION.md](STAGED_ACTIVATION.md)): a standalone
`gcloud run jobs update --update-secrets` against the worker job only,
after the budget caps are configured and the kill switch is rehearsed. It
is deliberately not part of any release command, so no routine deployment
can put a spendable credential in front of a runtime that is not yet
allowed to spend.

### Legacy provider bindings (the deployment stops before touching anything)

A provider key bound by an **earlier** release is not removed by this one:
the update is non-destructive, and `--update-secrets` never deletes a
binding it does not name. An earlier version of `scripts/deploy/cloud-run.sh`
bound `KIMI_API_KEY` to the worker job, so this is a realistic state of
production rather than a hypothetical one.

Detecting it in post-deployment verification would be too late — by then
both images are built, the worker job is deployed, the executor IAM binding
is written and the API is deployed. So `cloud-run.sh` runs
`require_no_live_provider_key_bindings` as the **last preflight gate**, in
both `check` and `apply` mode:

- it inspects the live API service **and** the live worker job;
- it detects `KIMI_API_KEY` and `MOONSHOT_API_KEY` as Secret Manager-backed
  bindings **and** as plain environment variables with literal values;
- it prints the resource, the variable name and the binding form — never a
  value of any kind;
- it exits non-zero **before** `gcloud builds submit`, before either deploy,
  before any IAM write and before any execution;
- a resource that does not exist yet is not a finding (nothing is bound to
  something that isn't there), but any other inspection failure — permission
  denied, for example — **fails closed**: "I could not look" is never
  treated as "there is nothing there".

The generated plan carries the same check as step 3, as two read-only
`describe | jq | grep` commands whose documented expected result is empty.

**The deployment never removes the binding for you.** Removal is destructive
and this release path is deliberately not, so it stays a separate, explicit
operator action with its own review.

First, inspect the live binding to learn which form it takes — the removal
flag differs, and the wrong one silently does nothing:

```bash
gcloud run jobs describe <WORKER_JOB> \
  --region <REGION> --project <PROJECT_ID> --format=json \
  | jq -r '(.spec.template.spec.template.spec.containers[0].env // [])[]
           | if .valueFrom.secretKeyRef then "secret \(.name)" else "env \(.name)" end' \
  | grep -E 'KIMI_API_KEY|MOONSHOT_API_KEY'
```

If the line begins with `secret`, the key is a Secret Manager binding:

```bash
gcloud run jobs update <WORKER_JOB> \
  --region <REGION> \
  --project <PROJECT_ID> \
  --remove-secrets KIMI_API_KEY
```

If it begins with `env`, the key is a plain environment variable:

```bash
gcloud run jobs update <WORKER_JOB> \
  --region <REGION> \
  --project <PROJECT_ID> \
  --remove-env-vars KIMI_API_KEY
```

Use `gcloud run services update <API_SERVICE> …` for the same removal on the
API service. Removing the binding does not delete the secret or its
versions — the Stage C material is untouched and stays available for the
Stage C operator action that introduces it deliberately.

**After removal, re-run the preflight before continuing:**

```bash
DEPLOY_MODE=check scripts/deploy/cloud-run.sh
```

It must report `Live provider-key check — … inspected.` for both resources
with no finding. Only then continue with the deployment (or with step 3 of
the generated plan).

### Gateway identity is required even while execution is disabled

`MILO_GATEWAY_AUDIENCE` and `MILO_APPROVED_GATEWAY_IDENTITIES` are deployed
with their approved values at Stage A, not left to whatever the service
happens to carry. `backend/production_config.py` fails startup in
production without them (`GATEWAY_AUTH_MISSING`), because the API's
read-only routes would otherwise trust a bare browser identity header —
execution being off does not make unauthenticated reads acceptable.
`cloud-run.sh` fails preflight when either is unset, when the allowlist is
empty or wildcarded, or when an entry is not a service account email;
post-deployment verification fails if either variable is missing from the
running service. Preserving an unknown existing value is not sufficient and
is not relied on.

## Private Cloud Run configuration

Proven by the templates in the generated plan plus
`check-gcp-resources.sh`:

- API: `--no-allow-unauthenticated`; invokers = gateway identity (and
  worker identity for internal routes) only.
- Worker job: private; invoker = API service account only.
- Separate service accounts for API and worker (validated; shared identity
  is BLOCKED).
- Revision naming: `--revision-suffix rel-<SHA12>` ties revisions to the
  release; traffic promotion is explicit (`--to-revisions`).
- Concurrency/instances/timeouts are deliberate template values
  (`--max-retries 0 --task-timeout 3600` for the job) — tune in the
  manifest copy, not ad hoc.

## Least-privilege IAM matrix

| Principal | Purpose | Roles (exact scope) |
| --- | --- | --- |
| Human deployment operator | run deployments manually | `roles/run.admin`, `roles/artifactregistry.writer`, `roles/iam.serviceAccountUser` **on the two runtime SAs only**, `roles/secretmanager.admin` on MILO secrets only |
| CI build identity | build/test only | **none in GCP** — CI never pushes images or deploys, by design |
| API runtime SA `<API_SERVICE_ACCOUNT_EMAIL>` | serve API, launch job | `roles/run.invoker` on `<CLOUD_RUN_WORKER_JOB>`; secretAccessor on Supabase + Redis secrets (secret-level) |
| Worker runtime SA `<WORKER_SERVICE_ACCOUNT_EMAIL>` | execute runs | `roles/run.invoker` on `<CLOUD_RUN_API_SERVICE>` (internal routes); secretAccessor on Supabase + provider + Redis secrets (secret-level) |
| Vercel gateway identity `<GATEWAY_IDENTITY_EMAIL>` | call private API | `roles/run.invoker` on `<CLOUD_RUN_API_SERVICE>`; `roles/iam.workloadIdentityUser` from the Vercel pool; **no Secret Manager access, no job access** |
| Logging/monitoring | read logs/metrics | `roles/logging.viewer`, `roles/monitoring.viewer` for the operator group |

Forbidden everywhere: `roles/owner`, `roles/editor`, project-wide
`iam.serviceAccountUser`, project-wide `secretmanager.secretAccessor`,
wildcard principals, browser identities with worker privileges, worker
identity with gateway privileges, shared gateway/worker identity — all
checked by `check-gcp-resources.sh`, `check-secret-metadata.sh`,
`validate_production_manifest.py` and `backend/production_config.py`.

## Migration gate

Execution deployment (Stage B+) is blocked unless: migration order valid
and complete (`check-migration-state.sh`), migration tests green
(PostgreSQL CI job, zero skips), remote state ∈ supported states, backfill
inputs ready where required, rollback prerequisites recorded
(`release.rollback_sha` in the manifest) and execution still disabled.
The gate never applies migrations itself.

## Health checks and revision verification

`GET /health` is unauthenticated-safe at the gateway, requires no secret
round-trip, triggers no provider/worker/run activity and exposes no
configuration. Deeper checks (DB/Redis reachability, configuration
classification) run server-side at startup
(`backend/production_config.py` fail-closed) rather than through a public
endpoint, so nothing sensitive is exposed via health.

Revision verification commands (also in the generated plan): service/job
`describe` for image digest + service account + env NAMES + secret
references, `services describe --format 'value(status.traffic)'` for
traffic allocation, IAM policy reads for private access, revision
timestamps, and digest comparison against the pushed `<FULL_SHA>` images.
Secret contents are never printed.

`scripts/deploy/cloud-run.sh` runs the same verification automatically at
the end of `DEPLOY_MODE=apply`, and exits non-zero on any failure. It
checks, for both the worker job and the API service:

| Verification | Failure condition |
| --- | --- |
| Full release SHA / image digest | running image is not the `<FULL_SHA>` tag, or does not resolve to that tag's registry digest |
| Service-account identity | job runs as anything but the worker SA; service runs as anything but the API SA |
| Environment variable names | a required Stage A variable is missing |
| Secret references | an expected `ENV=SECRET:VERSION` binding is missing, or `KIMI_API_KEY` is bound to the API |
| Preserved configuration | any variable or secret binding present before the deployment is gone afterwards |
| Stage A flags | `JOB_LAUNCHER` is not the selected mode, or any `MILO_ENABLE_*` is not `false` |
| Private IAM | the service or job policy contains `allUsers` / `allAuthenticatedUsers` |
| No worker execution | the job's execution count changed during the deployment |

The verification reads variable **names**, secret **references** and the
non-secret Stage A flag values only. It never calls
`gcloud secrets versions access` and never prints a secret value.
